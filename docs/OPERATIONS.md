# DuetSync operations

## Production layout

- Frontend: https://duetsync.vercel.app, Vercel project `duetsync` in the selected owner's team.
- WebSocket: `wss://wweuhpqsuwwcbgheckve.supabase.co/functions/v1/duet-sync`.
- Health: https://wweuhpqsuwwcbgheckve.supabase.co/functions/v1/duet-sync/healthz.
- Supabase project: `DuetSync`, isolated from other applications in the organization.
- Private room and quota tables: `duet_private` schema.
- Database maintenance: `duetsync-expired-state` cron job, every ten minutes.

The frontend is a production deployment, not a tunnel. Backend workers share PostgreSQL state instead of relying on process affinity. HTTPS/WSS protects traffic. Local media is not uploaded.

## Deploy a fork

1. Create a separate Supabase project and link its CLI project reference.
2. Apply the ordered checked-in migrations using `supabase db push`. The final migration state revokes anonymous RPC execution and grants execution only to `service_role`.
3. Set the exact production frontend origin in `supabase/functions/duet-sync/index.ts`. Do not use a wildcard origin.
4. Deploy with `supabase functions deploy duet-sync --no-verify-jwt`. This function performs capability-based authentication itself: room invitations and per-listener sessions are validated inside the message handlers. The platform's account-JWT gateway is intentionally not used for WebSocket handshakes.
5. Configure `DUET_SOCKET_URL` for the static build, and update the `connect-src` hostname in `vercel.json` to the new Supabase host.
6. Run tests and deploy the frontend with an authenticated Vercel account. Run the live browser test against the production origin before treating the release as verified.

The backend receives `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` from Supabase automatically. There is no custom credential to embed in source or copy to Vercel. Never expose the service-role key in frontend build variables or public assets.

The repository's `vercel.json` builds only the static frontend. GitHub source linking was unavailable in the connected Vercel account at initial release, so that release was uploaded through the deployment API. GitHub pushes currently run verification; they do not automatically deploy this product. Establish a Git login connection in Vercel if continuous deployment is desired.

## Optional self-hosted Node backend

For local development, `npm start` uses an in-memory store. A self-hosted durable Node deployment can supply `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` through its secret manager, then run with `NODE_ENV=production`. Supply an exact `ALLOWED_ORIGINS` allowlist and terminate TLS at a trusted reverse proxy. The local Node mode does not trust arbitrary forwarded IP headers; add a validated proxy-address strategy before exposing it behind a proxy. Hosted Supabase mode uses the platform-provided forwarded address for durable IP quotas.

Production startup refuses an unconfigured database. `.env.example` is a template; Node does not automatically load `.env.local`. Use a secret manager or `node --env-file=.env.local server.js` for a deliberately configured local durable instance. Do not commit that file.

## Health and incident response

- A successful `/duet-sync/healthz` returns `{"ok":true,"storage":"durable","version":"2.0.0"}`. It checks the database rather than only reporting that a process is alive.
- Logs contain structured failure event names (`upgrade_storage_error`, `room_storage_error`, `snapshot_storage_error`, `socket_error`) and timestamps, without room codes, audio contents, file names or listener tokens.
- On storage loss, clients pause instead of continuing uncoordinated playback. Check backend logs and database health, then allow clients to reconnect and tap Ready.
- On worker replacement, sockets reconnect with backoff. A reconnect must reclaim the same seat and re-establish audio readiness.
- If a creator loses the tab's session storage, create a fresh room. Room ownership cannot be recovered through an email address because there are no accounts.
- Review HTTP failure rates, database latency, active rooms and quota growth before increasing traffic. No external alerting/on-call system is configured in this release.

## Release and rollback

1. `npm ci`, `npm test`, `npm run test:e2e`, `npm run build`.
2. Deploy the backend from the reviewed source, then deploy the matching frontend.
3. Run the browser verification against the live URL and check health, private RPC denial and runtime logs.
4. Commit source, README, screenshots and verification evidence; push to GitHub.
5. If a release regresses, roll the frontend back to the prior Vercel deployment and redeploy the previous backend source. Preserve backward compatibility in database migrations; do not drop room tables to perform a rollback.

Keep credentials and Playwright traces out of the public repository. Screenshots generated by the included test use rooms that are explicitly ended after the test.

## Limits and security review

Room state uses atomic versioned updates and is checked before every privileged action. Public snapshots omit session hashes, invitation hashes and connection identifiers. Room creators own lock/end controls. Audio mismatch, missing readiness, stale revisions and replaced sessions are rejected server-side.

The deployed system enforces a 4 KB WebSocket payload, bounded pending-message queues, per-socket message rate limits, durable per-IP upgrade/join/create quotas, durable per-member action quotas, a slow-consumer cap, a 15-second join deadline, heartbeat leases and room expiration. These controls reduce common abuse; they are not a substitute for an independent security review or a sustained load test.

The default coordination model polls active room snapshots every 400 ms per worker and active room. Storage reads and serverless connection lifetime have cost and scaling implications. Push pub/sub, measured capacity planning and external alerts remain roadmap work.
